## Real stage and SQL

The former `payment_order_seat` timer wrapped exactly two operations:

1. `confirmOrderSeats`: a Java loop that calls MyBatis-Plus `orderSeatMapper.insert` once per seat;
2. one `seatLockMapper.markAsPurchased(orderNo, now)` call after the loop.

It contained no SELECT, precheck, snapshot mapping or other mapper call. The timer is now retained for historical comparison and mirrored by `payment_order_seat_total`; the two real operations are separately measured as `payment_order_seat_insert` and `payment_seat_lock_update`.

The successful stage SQL sequence is:

- 1 seat: one `order_seat` INSERT, then one `seat_lock` UPDATE (2 statements);
- 3 seats: three single-row INSERTs in loop order, then one UPDATE (4 statements);
- 6 seats: six single-row INSERTs in loop order, then one UPDATE (7 statements).

There is no explicit unique-check SELECT. InnoDB enforces the unique index during each INSERT.

Representative INSERT generated by `BaseMapper.insert`:

```sql
INSERT INTO order_seat
  (order_id, order_no, schedule_id, row_num, col_num,
   seat_label, active_sale_marker, create_time)
VALUES (?, ?, ?, ?, ?, ?, 1, ?);
```

The INSERT model is a Java for-loop of ordinary single-row mapper calls, not JDBC/MyBatis batch and not a multi-values INSERT.

The purchased-lock statement is:

```sql
UPDATE seat_lock
SET status = 2, update_time = ?
WHERE order_no = ? AND status = 1;
```

## DDL and plans

Actual `order_seat` indexes:

- `PRIMARY (id)` where `id BIGINT AUTO_INCREMENT`;
- `idx_order_seat_order (order_id)`;
- `idx_order_seat_schedule (schedule_id)`;
- `UNIQUE idx_order_seat_active_unique (schedule_id,row_num,col_num,active_sale_marker)`.

Paid-seat rows set `active_sale_marker=1`. Different seats in the same benchmark session therefore enter nearby ranges of the active unique index. No foreign keys exist on `order_seat`, so there is no FK parent lookup/lock to attribute.

Actual `seat_lock` indexes are PRIMARY, unique `(schedule_id,row_num,col_num)`, `(schedule_id,status)`, `(user_id,status)`, `(lock_token)` and `(lock_until,status)`. There is no index beginning with `order_no`. Read-only EXPLAIN showed:

- `SELECT ... WHERE order_no=? AND status IN (1,2)`: `type=ALL`, no possible key;
- purchased UPDATE: `type=index`, `key=PRIMARY`, `Using where`.

Thus the UPDATE locates rows by a full primary-index scan rather than by order number. No index or SQL was changed in this phase. An INSERT EXPLAIN was deliberately not used as a substitute for lock evidence.

MySQL ran with `REPEATABLE-READ`, `innodb_autoinc_lock_mode=2`, and `performance_schema=OFF` as configured. The latter was not changed.

## Lock evidence

| Run | Row-lock waits delta | Row-lock time delta | Waiting transactions peak | Deadlock marker changed |
|---:|---:|---:|---:|---|
| 710, 10 VU/1 seat | 62 | 830ms | 0 | no |
| 725, 25 VU/1 seat | 519 | 14,153ms | 5 | no |
| 723, 25 VU/3 seats | 499 | 51,611ms | 9 | no |
| 726, 25 VU/6 seats | 627 | 114,826ms | 11 | no |
| 711/716, 1 VU | 0 / 0 | 0 / 0ms | 0 / 0 | no / no |

This is direct concurrency-wait evidence: both 1 VU controls had zero new row-lock waits, while 25 VU produced hundreds of waits and active waiting transactions. At 25 VU/1 seat, the single-row INSERT P95 remained 2.867ms but the following seat-lock UPDATE reached 117.408ms. The result supports `SEAT_LOCK_UPDATE_WAIT`; it does not support unique-index, AUTO_INCREMENT or INSERT lock contention as the primary cause.

The InnoDB latest-deadlock marker stayed at the pre-existing `2026-09-22 15:52:16` value throughout every run. No new deadlock was observed. k6 reported zero system errors, timeouts, network errors and parse errors; independent-seat workloads produced no business conflict or duplicate-key response. No lock-timeout response occurred.

## Scaling and runtime

The INSERT P95 increased from 2.867ms to 5.964ms to 11.928ms for 1/3/6 seats at 25 VU, consistent with multiple single-row roundtrips, but remained small relative to the UPDATE. At 1 VU, six seats cost more INSERT time than one seat (30.278ms versus 8.880ms) without any row-lock wait. This is secondary per-seat overhead, not the primary contention source.

The purchased UPDATE is one statement per order, but its unindexed scan grows with fixture row volume and concurrent transactions. UPDATE P95 rose from 9.929ms at 1 VU/1 seat to 117.408ms at 25 VU/1 seat, and row-lock waits rose from zero to 519. More seats also mean more `seat_lock` rows to scan, matching the 369.033ms/419.299ms UPDATE P95 at 3/6 seats.

Hikari active/pending was 9/0 at 10 VU and 20/4 at each 25 VU run. The 25 VU pending connections coincide with measured InnoDB lock waits and long UPDATEs; Hikari pressure is a downstream symptom, not the primary cause. CPU peak/median was 15.545%/7.336% for the primary 25 VU one-seat run and was not saturated.

Order Create normally commits before a client can receive the order number and invoke Payment. Separate clients can still create other orders concurrently, but the profiled Payment orders were pre-created and independent, excluding overlap with Order Create for those rows. Payment holds its own order transaction and later performs the unindexed seat-lock UPDATE; no evidence showed a cross-service lock-order cycle.

The existing eight-way same-order Payment regression passed after instrumentation: one debit, payment record, PAID transition, ticket and PAID event. It is correctness evidence only and is excluded from throughput profiling.
